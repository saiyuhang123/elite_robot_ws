# Elite 打磨应用力控修改记录

## 1. 文档目的

本文记录 `src/elite_polish_app` 在接触搜索、SDK 闭环力控、轨迹桥接和安全退刀方面已经完成的修改，以及对应的实机验证结果。

本文以 2026-08-02 当前工作区代码和实机日志为准。状态分为：

- **已验证**：已经由实机日志证明修改生效。
- **待继续验证**：代码或参数已经修改，但尚未完成下一轮完整实机验证。
- **未处理**：只完成原因分析，尚未修改代码或参数。

## 2. 初始问题

### 2.1 位置接近导致碰撞报警

在 Git 版本 `97513f1570daf9212f64488bea0db7c4a5a77e3e` 中，机械臂使用位置轨迹逼近工件。接近速度和单步位移较大，刚性板接触后容易产生冲击，触发机械臂碰撞检测并停机。

### 2.2 首次加入 `startForceMode` 后过早进入力控

在 Git 版本 `0bd91d5cec2ff8be04e6968364e2d82f6e32e207` 附近开始接入 Elite SDK `startForceMode`。早期日志中出现：

```text
forcez_avg=-1.177 forcez_inst=-2.143
contact delta d -0.003000
force mode ENABLED
```

当时主要有以下问题：

1. 使用绝对力值判断接触，工具重力、安装倾角和传感器零漂会造成假接触。
2. 检测到接触后立即发布反向位置轨迹，同时几毫秒后启动力控，位置控制和力控存在重叠。
3. `startForceMode` 服务返回成功只代表 SDK 命令写入 socket，不代表控制器已经建立稳定闭环力。
4. 接近轨迹被高频新 goal 不断抢占，机械臂反复起步和减速，表现为长时间几乎不动。

## 3. 坐标系与力方向结论

机械臂为倾斜安装。当前工具 Z+ 轴在 base 坐标系下约为：

```text
(0.6691, 0.0000, 0.7431)
```

该方向对应世界坐标系 X+，也就是从预打磨位置朝工件逼近的方向。

Elite SDK 的 `wrench` 表示机器人施加给环境的力，和应用中传感器读到的反作用力符号相反。因此当前约定为：

- SDK `Fz > 0`：机器人沿工具 Z+/世界 X+ 压向工件。
- 应用 `relative_fz < 0`：传感器检测到工件对工具的反作用力。
- 力大时，SDK 闭环应沿世界 X- 回退。
- 力小时，SDK 闭环应沿世界 X+ 前进。

当前 `startForceMode` 使用固定参考系 `FIX`，只开放工具 Z 方向柔顺：

```text
selection_vector = [0, 0, 1, 0, 0, 0]
```

RX、RY、RZ 均不参与力控。

## 4. 接触搜索修改

### 4.1 预备位置局部去皮

机械臂到达预打磨位置并停止后：

1. 静置 `0.3 s`。
2. 采集 25 个力数据样本。
3. 计算当前姿态的局部 Z 向零点 `contact_fz_zero`。
4. 后续使用相对力判断接触：

```text
relative_fz = raw_fz - contact_fz_zero
```

该修改已经由实机日志验证。例如原始力 `raw_fz` 会随姿态出现约 `-4.8 N` 的基线，但去皮后的 `relative_fz` 可以保持在约 `0 N`，不会在未接触工件时误判。

状态：**已验证**。

### 4.2 多帧接触确认

当前接触条件为：

```text
relative_fz < -1.0 N
```

必须连续 8 个新的力传感器帧满足条件才确认接触。单个噪声尖峰不会触发状态切换。

状态：**已验证**。

### 4.3 低速、小步接近

接近阶段使用：

- 每步笛卡尔位移：`1 mm`
- 单步轨迹时间：约 `0.48 s`
- 实际接近速度：约 `2 mm/s`
- 最大搜索距离：`150 mm`
- 最大搜索时间：`90 s`

最初的 25 秒超时不足以覆盖接触搜索，先改为 70 秒、100 mm。加入工件平面拟合姿态后，实机在 100 mm 上限处仍未建立接触：

```text
travel=0.1000 relative_fz=0.134 confirm=0/8
contact search watchdog: travel=0.1000m (limit 0.1000)
```

因此将搜索行程改为 150 mm。按实测 100 mm 约需 52 秒计算，原 70 秒超时不能覆盖全部 150 mm，所以同步改为 90 秒。后续实机在约 106.9 mm 处建立接触：

```text
402 approach: travel=0.1069 relative_fz=-1.288 confirm=4/8
```

状态：**已验证**。150 mm 行程上限已使实机越过原 100 mm 保护点并在 106.9 mm 处接触工件；接近速度和力阈值未放宽。

### 4.4 接近 IK 求解容错

早期实现每个接近周期计算约 60 个插值点。TRAC-IK 单点超时就会中止，曾出现：

```text
contact approach IK failed or changed branch at point 36 (rc=-3)
```

修改后：

1. 每个周期只求解当前 1 mm 小步的终点。
2. 求解失败时依次尝试 `1.0`、`0.5`、`0.25` 倍步长。
3. 单次失败只记录警告并在下一周期重试。
4. 连续 5 个周期都失败才安全中止。

状态：**已验证**。修改后机械臂已稳定完成约 106.9 mm 接触搜索并确认接触。

## 5. 轨迹桥接修改

### 5.1 接近 goal 串行执行

原逻辑每 40 ms 发布一条持续约 0.48 s 的接近轨迹。新 goal 会抢占旧 goal，机械臂不断重新起步。实机曾在 25 秒内只移动约 2.4 mm：

```text
travel=0.0024m
time=25.00s
```

`elite_joint_trajectory_bridge` 现在识别 `frame_id == "contact_approach"`：

- 当前接近 goal 未结束时，丢弃重叠的接近 goal。
- 当前 1 mm 小步执行完成后才接受下一步。
- `force_contact_hold` 等安全保持轨迹仍可立即抢占接近轨迹。

状态：**已验证**。

### 5.2 正确解释 action 结果码

ROS 2 action 的 `CANCELED`，日志中的 code 5，在流式轨迹被新 goal 抢占时属于正常结果，不再作为控制器故障刷屏。

真正的 `ABORTED` 会输出控制器的 `error_code` 和 `error_string`。

状态：**已验证**。

## 6. 接触后切换力控

### 6.1 删除位置退让和力控重叠

确认接触后不再立即发布 `-3 mm` 反向位置轨迹。当前流程为：

1. 发布当前位置保持轨迹。
2. 保持时间 `0.25 s`。
3. 额外等待 action 完成余量 `0.20 s`。
4. 确认关节速度低于 `0.01 rad/s`。
5. 再调用 `startForceMode`。

增加 action 完成余量的原因是：实机中 `Trajectory succeeded` 比轨迹 `time_from_start` 晚约 50 ms。如果在 action 尚未完全结束时启动力控，随后的控制流程切换会干扰刚建立的力控状态。

状态：**已验证**。当前日志顺序已经变为：

```text
contact confirmed
Trajectory succeeded
force mode command sent
```

### 6.2 异步调用 SDK 服务

力控服务使用异步请求，避免在单线程 ROS executor 中同步等待 future 造成死锁。

已增加以下保护：

- 3 秒服务响应超时。
- 忽略已经失效的迟到响应。
- 异常、退刀和新命令开始前主动调用 `endForceMode`。
- 服务返回成功后仍不直接认为闭环已经稳定。

状态：**已验证**。

## 7. 力控建立验证

### 7.1 SDK 指令值与应用力值分开配置

实机发现 SDK 内部目标力与应用完成重力补偿、偏置修正和局部去皮后的 `relative_fz` 存在稳定差异：

```text
SDK 0.5 N  -> 应用 relative_fz 最终接近 0 N
SDK 2.0 N  -> 应用 relative_fz 最终约 -0.85 N
```

因此不再要求“SDK 设置 2 N，应用必须测到 -2 N”，而是分成两个参数：

```yaml
force_mode_wrench_z: 3.0
force_mode_sensor_target_fz: -1.5
```

含义分别为：

- `force_mode_wrench_z`：发送给 SDK 的内部施力目标。
- `force_mode_sensor_target_fz`：应用补偿和去皮后期望测到的实际反作用力。

### 7.2 开始切向运动前验证闭环

`startForceMode` 返回成功后，机械臂暂不启动打磨机和切向轨迹。只有满足以下条件才从子步骤 402 进入 403：

```text
relative_fz 位于 -1.5 ± 0.6 N
并连续稳定 0.5 s
```

如果 5 秒内不能建立目标力，则在开始板面横向运动之前安全退出。

实机验证日志：

```text
force-mode verification entered target band: relative_fz=-0.916
force-mode verification progress: relative_fz=-1.229
force mode VERIFIED: relative_fz=-1.539 stable_for=0.50s
```

状态：**已验证**。力控验证通过后，机械臂已经连续完成接近一整行、约 38 秒的板面运动。

## 8. 打磨过程安全监控

### 8.1 接触力过大

原实现直接使用单帧瞬时力与 `-5 N` 比较。实机中，力控已在约 `-1.07 N` 稳定，但打磨头 IO 开启约 0.35 秒后出现一次 `-5.40 N` 瞬时峰值，导致流程立即退出：

```text
force-mode watchdog: excessive contact force -5.400 N (limit -5.000 N)
```

当前改为两层过力保护：

1. 单帧瞬时力达到 `-15.0 N` 且**持续 `0.03 s`** 才退出。真实碰撞会持续远超 30 ms，仍会立即触发；而 125 Hz 力数据下单帧噪声尖峰（约 8 ms）会被拒绝。2026-08-02 实机曾出现单帧 `-17.193 N`、20 帧平均仅 `-2.766 N` 的尖峰直接触发硬保护，说明"单帧立即退出"对噪声过敏感，因此由立即退出改为持续确认。硬阈值先由 -7 N 调整为 -10 N，后按实机调试需求调整为 -15 N。
2. 20 帧滑动平均力达到 `-5.0 N`，并持续 `0.12 s` 才退出，拒绝电机启动的单次振动尖峰。

```yaml
force_mode_abort_fz: -5.0
force_mode_hard_abort_fz: -15.0
force_mode_hard_abort_confirm_time: 0.03
force_mode_abort_confirm_time: 0.12
```

注意：硬保护持续确认必须按**真实时间**计算（`steady_clock`），不能用"连续 N 次检查"计数，因为 403 阶段 watchdog 每 4 ms 调用一次、404 阶段每 40 ms 一次，按次数计数会对同一个尖峰产生不同结果。

状态：**代码已修改并编译通过，待实机验证启动振动和持续过力的区分效果**。

### 8.2 接触丢失

当：

```text
relative_fz > -0.15 N
```

持续超过 2 秒时，判定打磨头已经离开工件，关闭力控并安全退刀。

状态：**已验证**。早期 0.5 N SDK 目标无法维持接触时，该看门狗正确触发。

### 8.3 轴向补偿上限

轴向补偿定义为：实际 TCP 与“接触偏置后的名义轨迹”之间的位移，在力控轴方向上的投影。

首行实机运行约 38 秒后达到约 10 mm，原 10 mm 上限因此触发：

```text
force-mode watchdog: axial deviation 0.0100m exceeds 0.0100m
```

上限后来调整为 15 mm。在搜索行程放宽后的实机运行中，机械臂在 106.9 mm 处成功接触，SDK 力控也在目标带内稳定 0.5 秒：

```text
force mode VERIFIED: relative_fz=-1.249 stable_for=0.50s
```

但进入子步骤 404 的第一次监控时，当前实际 TCP 相对视觉名义路径的法向偏差约为 27 mm，立即触发原 15 mm 上限：

```text
force-mode watchdog: axial deviation 0.0270m exceeds 0.0150m (relative_fz=-1.232 N)
```

该时的接触力仍正常，不属于过力或失去接触。为先继续验证完整单行轨迹，当前已按实机调试需求将上限放宽为 40 mm：

```yaml
force_mode_max_axial_deviation: 0.040
```

并每秒输出一次：

```text
force-mode monitor: relative_fz=... axial_comp=... limit=0.0400m (...%)
```

注意：“力控验证后以实际接触位置作为动态轴向基准”目前只完成了方案分析，**尚未写入代码**。当前实际生效的修改仅是将原有轴向偏差上限从 15 mm 放宽到 40 mm。

放宽轴向位置上限没有删除其他保护，以下参数仍保持不变：

- 瞬时硬过力退出：`relative_fz <= -15.0 N`
- 硬过力持续确认：`0.03 s`
- 持续过力退出：20 帧平均力 `<= -5.0 N` 持续 `0.12 s`
- 失去接触：`relative_fz > -0.15 N` 持续 `2.0 s`
- 力控轴最大速度：`0.0005 m/s`

状态：**代码和配置已修改并编译通过，40 mm 上限待下一轮实机验证**。

### 8.4 中断后轨迹索引残留导致 404 从轨迹中段"续跑"

实机连续两次打磨日志显示：第一次打磨在 404 运行到第 839 步时被力看门狗（-17.19 N 硬过力）打断，退刀后重新下达打磨命令，第二次打磨 402 接触、403 开打磨机后，进入 404 的第一个周期就打印：

```text
[FATAL] curve polish target 840 lastQ, 34.321281, -103.481405, -95.118812, 67.825617, 71.081790, -26.216049
[FATAL] curve polish target 840 target, 0.334318, -105.515925, -90.482151, 61.926202, 94.389521, -1.092172
 polish job break
```

根因：

1. `forceModeWatchdog` 的退出路径只把 `sub_step_` 置为 405，不会重置 `polishcurve_step_index_` / `sidepolish_step_index_` / `polishcurve_yindex_`（重置只存在于正常完成和 FATAL break 分支）。
2. `resetForceContactState` 只重置接触检测、力控验证等状态，同样没有重置三个轨迹步进索引。
3. 于是第二次打磨 404 第一个周期直接取残留的 `target 840`（轨迹中段），而机械臂还停在接触点附近，TRAC-IK 求出的解与当前关节角差 34°（轴1）/25°（轴6），超过 `M_PI/10` 的"解连续"保护阈值，触发 `polish job break` 退刀。

修复：`resetForceContactState` 中新增

```cpp
polishcurve_step_index_ = 0;
sidepolish_step_index_ = 0;
polishcurve_yindex_ = 0;
```

保证每次新打磨命令都从轨迹起点开始。

状态：**代码已修改并编译通过，待下一轮实机验证**。

## 9. 安全退刀修改

原 406 退刀轨迹写死了 base 坐标系 Y+ 方向 100 mm 侧移。发生看门狗退出后，机械臂会突然大幅横移，容易被误认为力控随机漂移。

当前退刀流程改为：

1. 关闭力控。
2. 先沿力控轴反方向，即世界 X-，退出 `30 mm`。
3. 再沿世界竖直向上方向抬升 `150 mm`。
4. 最后回 Home/预打磨位。

相关参数：

```yaml
retract_axial_distance: 0.03
retract_lift_height: 0.15
```

状态：**已验证**。原来的 Y+ 100 mm 突然侧移已删除。

## 10. 当前单行打磨设置

当前试运行改为只打磨工件宽度中心的一行：

```yaml
polishproduct_width: 0.15
polishcurve_ycount: 1
```

当 `polishcurve_ycount` 为 1 时，目标行位于宽度中心，完成第一行后直接关闭打磨机并执行安全退刀，不再进入换道和第二行。

状态：**待继续验证**。该项为 YAML 运行参数，修改后无需重新编译，但必须重启节点。

## 12. 当前状态机时序

```text
到达预打磨位置
    ↓
等待静止并局部力去皮
    ↓
沿世界 X+ 以约 2 mm/s 搜索工件
    ↓
relative_fz < -1 N，连续 8 帧确认接触
    ↓
当前位置保持 0.25 s，并等待 action 完成余量 0.20 s
    ↓
startForceMode(Fz=+3 N, 仅工具 Z 轴柔顺)
    ↓
验证应用侧 relative_fz 在 -1.5±0.6 N 内稳定 0.5 s
    ↓
开启打磨机
    ↓
执行工件宽度中心的一行轨迹
    ↓
关闭打磨机和力控
    ↓
沿世界 X- 后退 30 mm
    ↓
世界竖直向上抬升 150 mm
    ↓
```

## 14. 工件平面 RANSAC 法向与贴面姿态

原实现使用三个 10×10 mm 小裁剪框的中心点叉乘法向，容易受单个小区域的深度噪声影响；同时 `tool_align_world: true` 会强制工具 Z+ 等于世界 X+，完全忽略工件实际倾角。

当前实现已经修改为：

1. 在 `target_box` 内使用 `SACMODEL_PERPENDICULAR_PLANE + RANSAC` 拟合工件面。
2. 约束平面法向必须位于世界 X+ 的 10° 范围内，避免把桌面等其它平面识别成工件面。
3. 对法向符号进行统一，使工具 Z+ 始终指向工件内部，不会在不同帧之间翻转。
4. 将世界竖直方向投影到拟合平面作为工具 Y 方向。
5. 由投影后的 Y 与工件法向构造工具 X，使单行扫掠方向保持接近世界 Y。
6. `tool_align_world` 默认改为 `false`，视觉输出四元数携带拟合后的工件倾角。
7. 接触搜索轴、SDK FIX 力控轴和轴向安全退刀均从该工具姿态自动获得，无需分别配置法向。

拟合结果必须同时通过以下质量门槛：

| 参数 | 当前值 | 含义 |
|---|---:|---|
| `plane_fit_distance_threshold` | `0.003 m` | RANSAC 内点距离阈值 |
| `plane_fit_max_iterations` | `1000` | 最大迭代次数 |
| `plane_fit_min_inliers` | `1000` | 最小内点数量 |
| `plane_fit_min_inlier_ratio` | `0.15` | 内点占目标 ROI 的最小比例 |
| `plane_fit_max_rms` | `0.0025 m` | 内点距离 RMS 上限 |
| `plane_fit_max_normal_angle_deg` | `10°` | 相对世界 X+ 的最大法向夹角 |

任一门槛不满足时，本次视觉任务返回失败，不会把不可信姿态发送给机械臂。成功时保存 `plane_fit_inliers.pcd`，并输出：

```text
[plane fit] OK: inliers=... ratio=... RMS=... angle_to_world_x=...deg
[plane fit] normal_base=(...) origin_base=(...)
```

已增加确定性的合成点云测试 `test/test_pcl_plane_fit.cpp`：输入相对世界 X+ 倾斜 3° 的平面并混入 500 个离群点。当前测试结果为内点率 98.0%、RMS 0.283 mm，最终工具 Z 与合成真实法向的误差低于输出精度，并且法向符号保持朝世界 X+。

最新实机运行中，拟合姿态最终传递到接触和 SDK 力控轴：


机械臂沿该轴完成约 106.9 mm 低速搜索、接触确认和力控稳定验证，说明点云法向到接触轴/力控轴的传递已在实机上生效。但砂盘是否在整行中完全贴合工件，仍需后续完整单行运行验证。

状态：**代码、编译、合成点云和实机法向传递已验证；整行贴面效果待继续验证**。

注意：RANSAC 解决的是“轨迹工具 Z 与工件法向不一致”。如果工具 Z 已与工件法向一致，但实体砂盘仍倾斜，则说明砂盘/连接件相对 TCP 存在固定安装角误差，还需要单独标定 TCP 姿态补偿。本次没有开放 RX/RY 力矩柔顺。

## 22. 2026-08-02 第六轮：侧向力保护通道 + Rx/Ry 旋转柔顺

两次 `averaged_overforce` 停摆的六维力诊断显示：侧向 Fx/Fy（10~15 N）先于 Fz 失控，并伴随显著力矩（刮边/法向不对齐的边缘接触特征），等 Fz 耦合超 -5 N 时打磨头已别紧。根因是力控只开放工具 Z（`selection_vector=[0,0,1,0,0,0]`），侧向和姿态无泄力通道，且 404 进给按控制周期无条件推进。

本轮两项修改：

1. **watchdog 侧向力通道**：`forceModeWatchdog` 在 -5N 平均过力分支后新增并列分支，20 帧平均侧向合力持续超阈值即按同一流程退出（`disableForceMode` + 关打磨机 + 回 Home），诊断原因为 `lateral_overforce`。判定用预备姿态去皮后的**相对值** `sqrt((fx-fx0)²+(fy-fy0)²)`（fx0/fy0 与 fz 去皮同源、同批采样）；每秒监控日志新增 `lateral_avg` 便于调阈值。

   **注意**：首版用绝对值判定，实测接触状态下静态偏置已达 10.2 N（重力模型残差，悬空时 fz 残差也有 -5.6 N），切向未动即误触发。相对值判定与 `relative_fz` 同一哲学，必须保留。

   ```yaml
   force_mode_abort_lateral_f: 8.0               # 平均侧向合力相对值阈值(N)
   force_mode_lateral_abort_confirm_time: 0.12   # 持续确认时间(s)
   ```

2. **Rx/Ry 旋转柔顺**（`force_mode_rot_compliance: true` 时）：`startForceMode` 的 `selection_vector` 变为 `[0,0,1,1,1,0]`，Rx/Ry 目标力矩 0，角速度受 `force_mode_rot_vel_limit`（默认 0.05 rad/s ≈ 3°/s）限制。零力矩目标让端面缓慢贴合板面（稳态转角≈板子倾角），消除法向不对齐造成的边缘接触/侧向拖曳；Rz 保持位置模式，扫掠方向不受影响。`false` 可退回纯 Z 力控。

   ```yaml
   force_mode_rot_compliance: true
   force_mode_rot_vel_limit: 0.05
   ```

验证要点：对比同一块板打磨中的 avg_fx/avg_fy 是否从 10 N 级降到 1~2 N 级；观察开启柔顺后姿态是否缓变无突变；若出现扫掠中姿态抖动（SDK 力控无阻尼参数），减小 `force_mode_rot_vel_limit`。

**A/B 结论（2026-08-02 实机两轮）**：开启旋转柔顺后，两轮均在随机位置（step=114/241，扫掠 22mm/48mm 处）出现单帧 -27~-36 N 撞击尖峰 + 指数衰减、随后力二次爬升触发 -5 N 退出；而开启前两次停摆均为无尖峰的渐进爬坡。怀疑无阻尼旋转柔顺在扫掠中振荡啃边，默认改回 `false`。长期方案：板法向已由视觉 RANSAC 每跑对齐（第 14 节），剩余偏差是砂盘/连接件相对 TCP 的固定安装角（工具系常量，与车位/板位姿无关），走一次性测定补偿，不再用在线柔顺。

状态：**侧向通道（相对值判定）已编译通过待继续验证；旋转柔顺 A/B 后默认关闭，安装角补偿待做**。

## 23. 2026-08-02 第七轮：应用层慢姿态环（替代 SDK 旋转柔顺）

第六轮 A/B 后再跑一轮（`rot_comp=0`）：撞击尖峰消失，坐实尖峰来自 SDK 旋转柔顺；但出现渐进 dig-in（`recent_fz` -5 → -15.8 N 爬坡，瞬时侧向合力 > 法向），与改动前的老停摆形态一致。六维力显示停摆时一半以上的力垂直于力控 z 轴，2mm/s 的 z 向退让救不回来。机理判断：砂盘/连接件相对 TCP 的固定安装角（工具系常量，与车位/板位姿无关）使盘面倾斜，扫掠中边缘接触，旋转盘摩擦力自增强。

SDK 旋转柔顺思路对但实现无阻尼不可用，故在应用层自实现慢姿态环：

- 404 每控制拍（40ms）取 20 帧平均力矩 Mx/My，超出死区 0.10 N·m 的部分按 `d = -gain·M·dt` 积分（增益 0.007 rad/(N·m·s)），累积为轨迹姿态修正（绕 TCP 原点右乘旋转，不动位置）
- 变化率限 0.5°/s、总限幅 ±2°：只追准静态贴合误差，百 ms 级应用层延迟对该时间尺度无影响；快扰动仍由 z 向力控和 watchdog 处理
- 符号约定：接触点偏 +x → My>0 → 需绕 y 负转抬起 +x 边。若实机力矩不收敛反发散，首先怀疑符号，将 `orient_adapt_gain` 取反即可
- 每次打磨命令/中断/完成时修正量清零
- 每秒 monitor 日志升级为六维：`lat=(fx,fy)|合力| tq=(mx,my) adapt=(rx,ry)deg`，平静期力矩数据同时供安装角固定补偿测算

```yaml
orient_adapt_enabled: true
orient_adapt_gain: 0.007
orient_adapt_torque_deadband: 0.10
orient_adapt_max_angle: 0.035
orient_adapt_max_rate: 0.009
```

验证要点：monitor 中 `tq` 是否被慢环压向 0、`adapt` 是否缓变收敛（不来回振荡）；若收敛后 `tq` 仍有稳定残余，其方向和大小即安装角，可做一次性固定补偿；若 dig-in 仍发生，比较发生时的 `adapt` 是否已到限幅。

**实机结论（2026-08-02 一轮）**：环机械执行正常（adapt 缓变至 1.44°），但 mx 全程不收敛——平静期力矩大头是侧向摩擦力 × 传感器到盘面杠杆臂（h≈0.12m 模型与实测逐点吻合），转姿态无法消除，环持续积分至砂盘边缘咬住，撞出 -42 N 单帧尖峰，与 SDK 旋转柔顺同一死法。**力矩驱动的姿态自适应（任何层）均不可用，默认关闭。** 后续若重启需先做摩擦力矩补偿（M' = M - h×F_lat 再积分）。渐进 dig-in（改动前的老问题）仍是主敌，当前最大嫌疑为砂盘跳动/变形/磨损不均，先查机械，再考虑 `force_mode_z_vel_limit` 2→4mm/s。

状态：**已关闭并编译通过；撞击类停摆根因已查明（力矩驱动的姿态自适应），渐进 dig-in 待机械排查**。

涉及文件：`config/polish_params.yaml`、`src/ysURForceAppControl.cpp`、`include/ysURForceAppControl.hpp`。

## 24. 2026-08-02 第八轮：进给门控 + z 向退让提速 4mm/s

第七轮结论后实机一轮（姿态全关）：跑满 17.44s（当时最长）后停摆，`recent_fz` 仍以 >-21.5 N 尖峰（峰值在 24 帧窗口外）开头、衰减到 -4.5 后**二次爬升**至 -8.76 触发 -5 N 退出。尖峰在姿态全关下仍出现，修正第七轮结论：姿态自适应是撞击的放大器而非根源，根源在机械/摩擦自激侧（粘滑特征：全程 fz ±2N 摆动，停摆前 10s 抓到一次 relative_fz=+1.19 瞬间卸载弹跳）。砂纸经查无问题。

历次 `averaged_overforce` 停摆的共同直接死因是**尖峰后的二次爬升**：404 轨迹索引按控制周期无条件推进（`force_mode_enabled_ || 距离<1mm` 即 index++），力突增时切向照走，把打磨头压着走。本轮两项对策：

1. **进给门控**（`feed_gate_enabled`）：404 每拍检查 20 帧平均力，`<= feed_gate_fz`（-4 N，高于 -5 N 退出线）即暂停推进轨迹索引，目标保持当前点，等 z 向力控拉回带内再自动继续；门控状态约 1s 一条 WARN；持续超 `feed_gate_timeout`（3s）按正常流程退出（诊断原因 `feed_gate_timeout`），防产线悬死。
2. **z 向退让提速**：`force_mode_z_vel_limit` 0.002 → 0.004（0.5→2→4mm/s 渐进，前两档无振荡），尖峰后力控退得更快，配合门控吸收二次爬升。

验证要点：日志出现 `feed gated` 后能否看到 `fz_avg` 回落、推进自动恢复；门控触发后是否还会走到 -5 N 退出；若出现力控振荡（fz 高频大幅度摆动）先把 `force_mode_z_vel_limit` 回退到 0.002。

状态：**代码已修改并编译通过，待实机验证**。

## 25. 2026-08-02 第九轮：收工不退刀的时序竞争修复

实机一轮打磨完整跑完（1500 步，尾声过载由进给门控兜住），但收工时回退轨迹被控制器取消（`Current goal cancelled during deactivate transition`），机器人停在板上不动。根因：`polish_endPolishtool`（405）中 `disableForceMode()` 发完 endForceMode 请求**不等响应**即返回，约 60ms 后 406 发布回退轨迹；驱动端 endForceMode 触发控制器 deactivate/activate 切换，切换途中到达的 goal 被取消。成功/失败仅差十几 ms 时序（历次异常退出日志末尾的同一行 error 均为此因）。

修复：

- `disableForceMode()` 增加响应跟踪（`force_mode_disable_pending_/done_` 回调置位；无力控活动或服务不可用时直接置完成，不阻塞）
- `polish_endPolishtool` 改两阶段：首拍关工具+发 disable 并返回；后续拍等 disable 响应到达后再静置 `retract_disable_settle_time`（默认 1.0s，yaml 可调）才进 406；5s 超时兜底（WARN 后照常退刀，不悬死产线）
- `enableForceMode` 时清除上一轮 disable 痕迹，防陈旧 done 误放行

本轮同一次运行还观察到 `axial_comp` 全程 27mm（67%上限），而上一轮成功运行仅 4%——即修改记录第 294 行记载的"接触点与视觉名义路径约 27mm 差异"间歇性复现，与力事件的相关性待结合 `404 start self-check` 的 `start_axial_err` 进一步定位（开局即 0.027 → 接触偏移未吃到名义轨迹；开局近 0 渐增 → 名义轨迹与板面角度偏差）。

状态：**代码已修改并编译通过，待实机验证**。

涉及文件：`config/polish_params.yaml`、`src/ysURForceAppControl.cpp`、`include/ysURForceAppControl.hpp`。

## 26. 2026-08-02 第十轮：视觉平面拟合鲁棒化

实机发现板子挪动几厘米后，固定 `target_box` 裁剪框会压到板边/夹具/杂物，RANSAC 被窄条带歪——打磨位置偏几厘米且工具与板面不平行。根因是结构性的：①裁剪框固定；②法向 10° 约束对"板边/墙面等同法向结构"无甄别力；③只查内点数量不查覆盖形状；④单平面假设（板后半段弯，另由运行时轨迹自适应解决）。

`pclCalcTransform.hpp` 两项升级：

1. **迭代重拟合**：RANSAC+质量门（内点数/比例/法向角/RMS）抽成 `fitPlaneOnce()`；首遍拟合后在首遍内点上再拟合一遍，离面污染点被剔除。第二遍不过质量门则回退首遍，不会更差。
2. **内点覆盖面校验**：在平面局部系（x=扫掠向、y=竖直向）用 1%/99% 分位边界算内点覆盖范围，小于 `plane_fit_min_extent_x/y` 判失败——内点只是一窄条（板边/棱）时宁可视觉失败重拍，不拿歪拟合去打磨。

```yaml
plane_fit_refit_enabled: true
plane_fit_min_extent_x: 0.12   # m, 按板面在框中的预期覆盖调
plane_fit_min_extent_y: 0.10
```

合成点云测试 `test_pcl_plane_fit` 扩充：正例（3° 倾斜平面+500 离群点，两遍拟合通过，角度误差 0°）+ 负例（0.02m 窄条，被覆盖面校验正确拒绝），均通过。

注意：若实机出现 `[plane fit] FAIL: inlier extent too small`，说明裁剪框压到板边，应重摆板或调整 `target_box`，而不是放宽 extent 阈值。

状态：**代码已修改、编译与合成点云测试通过，待实机验证**。

涉及文件：`include/pclCalcTransform.hpp`、`src/ysCamera3DSolver.cpp`、`include/ysCamera3DSolver.hpp`、`config/polish_params.yaml`、`test/test_pcl_plane_fit.cpp`。
